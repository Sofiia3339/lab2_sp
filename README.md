# Лабораторна робота: профілювання, оптимізація та оцінка енерговитрат програми згладжування показів датчика на Intel macOS.

## Дослідження програми згладжування показів датчика


У роботі порівняно виконання однієї програми мовою C, скомпільованої з параметрами `-O0` та `-O3`. Досліджено час, використання пам’яті, профілі функцій, асемблерний код та оцінені енерговитрати процесорного пакета.

Дослідження виконано в macOS. Замість Linux `perf` використано `sample`, Instruments Time Profiler і доступну статистику штатної команди `/usr/bin/time -l`. Ці інструменти не відтворюють повністю набір можливостей `perf stat -d`.

## Середовище

- MacBook Pro 16″, 2019.
- Intel Core i9-9880H, 2,30 GHz, 8 ядер.
- 16 ГБ оперативної пам’яті.
- macOS Tahoe 26.6.2.
- У збереженому `compiler.txt` зафіксовано Apple clang 21.0.0.
- Інструменти: `time`, `sample`, Instruments Time Profiler, `powermetrics`, FlameGraph Brendan Gregg.

Версія активного компілятора після встановлення Xcode може відрізнятися від збереженої версії; нові запуски потрібно супроводжувати власними відомостями про середовище.

## Програма

Програма `smooth.c` створює масив із 4 000 000 цілих показів. Початкові дані генеруються детерміновано, тому за однакових параметрів запуски отримують однакові вхідні значення.

Функція `smooth` обчислює середнє п’яти сусідніх значень:

```c
b[i] = (a[i - 2] + a[i - 1] + a[i]
      + a[i + 1] + a[i + 2]) / 5u;
```

Ділення цілочисельне. Перші та останні два елементи копіюються. Дані читаються з одного масиву, а результат записується в інший. Після кожного проходу масиви міняються ролями.

Кількість проходів задається аргументом командного рядка. Повторне згладжування використано як навчальне навантаження для вимірювання продуктивності. Наприкінці програма друкує контрольну суму. Атрибут `noinline` залишає `smooth` окремою функцією для профілювання в обох збірках.

## Компіляція та запуск

Потрібні Command Line Tools for Xcode або повний Xcode. Для Instruments потрібен повний Xcode. Команди виконуються в папці з `smooth.c`.

```bash
clang -std=c11 -O0 -g -fno-omit-frame-pointer smooth.c -o smooth_O0
clang -std=c11 -O3 -g -fno-omit-frame-pointer smooth.c -o smooth_O3
```

Основне навантаження:

```bash
./smooth_O0 10000
./smooth_O3 10000
```

В обох версіях для 10 000 проходів отримано:

```text
Samples: 4000000
Passes: 10000
Checksum: 18416936058326190937
```

Збіг контрольних сум є перевіркою результату для протестованих даних, а не доведенням правильності для всіх можливих входів.

## Час і статистика виконання

Приклад нового вимірювання зі збереженням результатів в окрему папку:

```bash
mkdir -p results/mac/reproduction
/usr/bin/time -l ./smooth_O0 10000 > results/mac/reproduction/output_O0.txt 2> results/mac/reproduction/time_O0.txt
/usr/bin/time -l ./smooth_O3 10000 > results/mac/reproduction/output_O3.txt 2> results/mac/reproduction/time_O3.txt
```

- `real` — повний час виконання.
- `user` — процесорний час у користувацькому коді.
- `sys` — процесорний час ядра на обслуговування програми.
- `maximum resident set size` — максимальна резидентна пам’ять; у цих звітах значення наведено в байтах.
- `instructions retired` і `cycles elapsed` — доступні на цьому Mac лічильники виконання.

У першій парі основних запусків кількість виконаних інструкцій становила 1 200 241 812 866 для O0 та 170 094 607 326 для O3. Кількість тактів — 628 822 792 522 та 67 308 239 093 відповідно. Промахи кешу та помилки передбачення переходів цим дослідом не вимірювалися.

## FlameGraph

Використано сторонні інструменти Brendan Gregg:

```bash
git clone https://github.com/brendangregg/FlameGraph.git
```

Приклад збору нового профілю O3:

```bash
mkdir -p results/mac/reproduction
./smooth_O3 10000 > results/mac/reproduction/profile_output_O3.txt &
profile_pid=$!
sample "$profile_pid" 5 1 -file results/mac/reproduction/sample_O3.txt
wait "$profile_pid"
```

Перетворення стеків і створення SVG:

```bash
awk -f FlameGraph/stackcollapse-sample.awk results/mac/reproduction/sample_O3.txt > results/mac/reproduction/folded_O3.txt
perl FlameGraph/flamegraph.pl results/mac/reproduction/folded_O3.txt > results/mac/reproduction/flamegraph_O3.svg
open results/mac/reproduction/flamegraph_O3.svg
```

Для O0 використовується та сама послідовність із відповідними назвами програми та файлів. Процес має працювати протягом усього інтервалу збору вибірок.

Підготовлено `flamegraph_O0.svg` і `flamegraph_O3.svg`. Прямокутники показують кадри стека, вертикальне розташування — вкладеність викликів, ширина — частку вибірок із відповідним кадром. Горизонтальна вісь не є часовою шкалою.

У записані фрагменти обох версій потрапила переважно `smooth`, тому початкові SVG мають майже однакову структуру. Це не заперечує прискорення: графіки нормовані на власні набори вибірок. Абсолютний час порівнюється окремо. Профіль `sample` не слід автоматично вважати тотожним CPU-профілю Linux `perf`.

## Instruments Time Profiler

Збережено профілі `O0.trace`, `O3.trace` та скриншоти. Для вибраного діапазону отримано:

| Показник | O0 | O3 |
|---|---:|---:|
| Загальний Weight процесу | 3,04 с | 437 мс |
| Weight і Self Weight функції `smooth` | 3,00 с | 414 мс |
| Частка `smooth` | 98,8% | 94,7% |

`smooth` залишається основною обчислювальною функцією. У збірці O3 `fill_data` та `checksum` вбудовано в `main`.

Значення Weight є оцінками за вибірками та залежать від вибраного діапазону. Ці профілі отримано в окремому досліді; їх не змішано з часом основних енергетичних запусків.

## Асемблер і оптимізація

Асемблер отримано командами:

```bash
clang -std=c11 -O0 -S -masm=intel smooth.c -o assembly_O0.s
clang -std=c11 -O3 -S -masm=intel smooth.c -o assembly_O3.s
clang -std=c11 -O3 -march=native -S -masm=intel smooth.c -o assembly_native.s
```

| Ознака основного циклу `smooth` | O0 | O3 | O3 з `-march=native` |
|---|---|---|---|
| Обчислення | Один вихідний елемент | SIMD із XMM | SIMD із YMM |
| Ширина векторів | — | 128 біт | 256 біт |
| 32-бітних елементів у векторі | — | 4 | 8 |
| Вихідних елементів за основну ітерацію | 1 | 8 | 32 |
| Ділення на 5 | `div` | Множення і зсуви | Множення і зсуви |

В O0 багато повторних завантажень адрес та індексу зі стека. В O3 використано регістри, векторизацію та обробку кількох груп за ітерацію. Інструкції `movdqu`, `paddd`, `pmuludq` працюють із XMM; використовується SSE-сімейство, зокрема `pblendw` із SSE4.1. Ділення на сталу замінено послідовністю множення, перестановок та зсувів зі збереженням цілочисельного результату.

В `assembly_native.s` є 256-бітні цілочисельні операції AVX2: `vpaddd`, `vpmuludq`, `vpsrld`, а також завантаження і записи `vmovdqu`. Основний цикл обробляє чотири вектори по вісім вихідних елементів.

Збірка `native` є окремим прикладом AVX2. Наведені нижче результати часу та енергії належать до звичайних O0 і O3. Час та енерговитрати `native` окремо не порівнювалися.

## Методика оцінки енергії

Використано:

```bash
sudo powermetrics --samplers cpu_power -i 1000
```

Аналізувався показник:

```text
Intel energy model derived package power (CPUs+GT+SA): …W
```

Це модельна оцінка потужності процесорного пакета: CPU, інтегрованої графіки GT та системного агента SA. Вона не охоплює весь ноутбук і не є прямим обліком окремого процесу.

Стабільний фон виміряно за 30 інтервалами загальною тривалістю 30,12467 с. Середня фонова потужність, зважена за тривалістю інтервалів, становила приблизно 0,64966 W.

Для кожної версії виконано три запуски з 10 000 проходів. `powermetrics` працював паралельно з програмою. Початок та завершення запусків зафіксовано через Perl `Time::HiRes`. Для середньої потужності відібрано лише інтервали, які впевнено містилися всередині запуску, з урахуванням секундної точності заголовків логів. Середнє зважено за тривалістю інтервалів.

Оцінки розраховано так:

```text
E пакета ≈ середня потужність внутрішніх інтервалів × real
E додаткова ≈ (середня потужність − фонова потужність) × real
```

Це екстраполяція на весь запуск, а не точне інтегрування від старту до завершення. Додаткова енергія є оцінкою внеску навантаження понад фон. На неї впливають стороння активність, сталість фону, часова дискретність і модель вимірювача. Енергію всього ноутбука та точну енергію виключно процесу в цій роботі не виміряно.

## Результати

| Показник | O0 | O3 |
|---|---:|---:|
| Середній `real`, с | 143,98 | 18,61 |
| Діапазон `real`, с | 143,11–145,40 | 18,56–18,71 |
| Стандартне відхилення `real`, с | 1,24 | 0,084 |
| Середня потужність пакета, W | ≈21,642 | ≈14,410 |
| Середня оцінена енергія пакета за запуск, J | ≈3116,3 | ≈268,2 |
| Середня оцінена додаткова енергія понад фон, J | ≈3022,7 | ≈256,1 |

Прискорення за відношенням середніх часів становить приблизно **7,74 раза**. Середня оцінена енергія процесорного пакета зменшилася приблизно на **91,4%**.

Стандартне відхилення характеризує розкид між трьома запусками, а не повну похибку методики. Середні енергетичні підсумки приблизні: значення першої пари враховано з округленням попереднього аналізу.

## Висновок

Оптимізація O3 зберегла контрольний результат та значно скоротила час виконання. У фактичному асемблері виявлено векторизацію, ефективніше використання регістрів, обробку кількох груп за ітерацію та заміну ділення на сталу.

У профілях основне навантаження залишилося у функції `smooth`. У досліджених запусках скоротилися і тривалість виконання, і середня потужність процесорного пакета, що зменшило оцінену енергію. Вимірювання показують сумарний ефект оптимізацій і не виділяють окремий внесок кожного перетворення.
